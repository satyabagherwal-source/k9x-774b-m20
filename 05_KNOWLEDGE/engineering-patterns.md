# Engineering Patterns

This directory contains generalized, reusable engineering patterns extracted from validated real-world software development outcomes. These patterns provide architectural guidance and implementation rules to prevent recurring defects in asynchronous execution, state management, resource lifecycles, and system interfaces.

---

## 1. Async In-Flight Fresh-State + Targeted Field Scoping

**RULE**:
When writing asynchronous background tasks or pipeline handlers that persist updates after an async wait, ALWAYS re-fetch the latest entity record from storage immediately before persisting, and patch ONLY the specific fields generated by the task. NEVER spread a stale pre-wait entity snapshot.

**WHY**:
Prevents silent data loss when user edits or concurrent state updates occur during an in-flight asynchronous operation.

**WHEN TO APPLY**:
Any asynchronous task that reads domain state, crosses an async boundary (network HTTP fetch, queue wait, database query), and later persists changes.

---

## 2. Event-Driven Cascade Resource Cleanup

**RULE**:
When a parent domain entity is deleted or retired, dependent services that own related resources MUST receive an explicit lifecycle event and clean up their timers, queued work, child records, subscriptions, and other owned resources.

**WHY**:
Prevents orphan timers, orphan storage records, memory/resource leaks, and stale background work.

**WHEN TO APPLY**:
Whenever domain resources (timers, background workers, notification logs, child records) are distributed across decoupled services or subsystems.

---

## 3. Idempotent Schedule Registration + Active Countdown Preservation

**RULE**:
Scheduler registration and rescheduling operations MUST be idempotent for the same entity and MUST preserve the currently intended active countdown when configuration has not meaningfully changed. Re-registering an already scheduled task must not reset its effective timing accidentally.

**WHY**:
Prevents timer countdown resets, duplicate timers, and inconsistent scheduler state.

**WHEN TO APPLY**:
Any timer, polling loop, retry mechanism, scheduled-job engine, or background-task system.

---

## 4. Reactive Mutation Subscriptions for Derived View State

**RULE**:
When a UI component derives display state from an external store or service, the component MUST have an explicit reactive synchronization mechanism that causes the derived view to refresh after relevant mutations. Do not rely on static context references alone when the underlying external store can change independently.

**WHY**:
Prevents stale UI views where storage mutations succeed but the screen fails to render updated state until manual page refresh.

**WHEN TO APPLY**:
React or other UI systems consuming local storage, custom stores, repositories, event emitters, or non-reactive service layers.

---

## 5. Defensive Boundary Deserialization + Exception Isolation

**RULE**:
Data crossing an application trust boundary (browser storage, API payloads, configuration files, user input) MUST be treated as untrusted and potentially malformed. Parsing, deserialization, and domain object construction operations that can throw exceptions MUST be isolated behind defensive validation and error boundaries. Invalid external input MUST NOT be allowed to crash unrelated application boot, rendering, or lifecycle execution. The boundary handler MUST provide deterministic safe fallbacks or controlled rejection behavior.

**WHY**:
Prevents malformed external payloads, corrupted cached strings, or invalid user inputs from escalating into unhandled runtime exceptions that break application availability.

**WHEN TO APPLY**:
Any boundary where external data is parsed, deserialized, or constructed into domain models (JSON deserialization, string parsing, storage hydration, API request handling, configuration loading).

---

## 6. Interface & Build Contract Consistency

**RULE**:
Before implementation or integration, verify that every consumer expectation is satisfied by the corresponding provider, component interface, service delegation layer, and build/module configuration. Required methods, props, delegated operations, and module aliases must remain contract-compatible.

**WHY**:
Prevents runtime missing-method failures, component prop interface mismatches, and build/import resolution failures.

**WHEN TO APPLY**:
Services, repositories, adapters, UI components, APIs, wrappers, SDKs, module aliases, and build configurations.

---

## 7. Service-Level Input Preconditions + Domain Constraint Guards

**RULE**:
State-changing service operations MUST independently enforce their required input preconditions and domain constraints before mutation. Do not rely solely on UI validation because service methods may be called by other callers, tests, background tasks, or future APIs.

**WHY**:
Prevents invalid data, duplicate records, malformed schema state, and domain-inconsistent persistence.

**WHEN TO APPLY**:
Any service, repository, or API operation that creates, updates, deletes, or otherwise mutates domain state.

---

## 8. Collision-Resistant Entity Identity Generation

**RULE**:
Entity identifiers MUST NOT rely on timestamp resolution alone. Identity generation strategies MUST employ collision-resistant mechanisms appropriate to the architecture, such as UUIDs (`crypto.randomUUID()`), database-backed sequence/uniqueness constraints, cryptographic hashes, or atomic sequence counters. While appending pseudo-random entropy to timestamps reduces collision probability in client-side or mock contexts, it does not guarantee absolute uniqueness and must not replace true uniqueness constraints in production storage architectures.

**WHY**:
Prevents duplicate primary keys, entity identity collisions, and unintended cross-record mutations during rapid or concurrent creation cycles.

**WHEN TO APPLY**:
Entity creation, primary key generation, temporary client-side IDs, job/queue task identifiers, uploaded file naming, and distributed resource identity.
