# PART 2 --- AI-BUILDER-BRAIN की मूल पहचान

## 2.1 यह AI Model नहीं है

AI-Builder-Brain स्वयं कोई AI Model, Foundation Model, Chatbot या Autonomous AI Agent नहीं है।

यह एक:

**Universal, Model-Independent, Evidence-Based, Continuously Evolving Construction Intelligence Data System है।**

यह एक व्यापक Structural Intelligence Infrastructure है जिसमें किसी भी Compatible AI को वास्तविक निर्माण के लिए आवश्यक ज्ञान, अनुभव, सिद्धांत, प्रक्रियाएँ, नियम, कौशल, Patterns, Relationships, Constraints, Evidence और Verification Methods उपलब्ध कराए जाते हैं।

इसका उद्देश्य किसी AI को केवल अधिक Documents देना नहीं है।

इसका उद्देश्य उस AI की वास्तविक निर्माण क्षमता को विस्तारित करना है।

## 2.2 केंद्रीय सिद्धांत

AI Model और AI-Builder-Brain अलग-अलग संस्थाएँ हैं।

-   AI Model: Reasoning, Language Understanding, Planning और उपलब्ध Model Capabilities प्रदान करता है।
-   AI-Builder-Brain: Structured Knowledge, Construction Intelligence, Experience, Skills, Rules, Relationships और Verified Procedures उपलब्ध कराता है।
-   External Tools: वास्तविक Research, Coding, Execution, Design, Testing, Deployment और अन्य Actions करते हैं।
-   Real-World Products: वास्तविक उपयोगकर्ताओं की समस्याएँ हल करते हैं और Feedback उत्पन्न करते हैं।

केंद्रीय संबंध:

AI Model + AI-Builder-Brain + Tools + Evidence + Execution + Verification = Enhanced Construction Capability

Brain किसी एक Model में बंद नहीं होगा।

भविष्य में GPT, Gemini, Claude, Groq, Open-Source Models या किसी नए AI Architecture से इसे जोड़ने की संभावना होनी चाहिए।

**Brain अलग, AI अलग और Brain से Intelligence प्राप्त करने का Interface अलग रहेगा।**

## 2.3 अंतिम Mission

Universal Construction Intelligence विकसित करना, जिससे कोई Compatible AI केवल निर्माण का उद्देश्य प्राप्त करके आवश्यकता समझने, Research करने, कल्पना करने, Design तैयार करने, Architecture चुनने, निर्माण करने, जाँचने, सुधारने, Launch करने, Operate करने और भविष्य में विकसित करने की पूरी प्रक्रिया स्वयं संभाल सके।

# PART 6 --- Universal Internet Knowledge Acquisition

## 6.1 केवल GitHub से ज्ञान नहीं लेना है
GitHub की 10,000 Repositories का कार्यक्रम एक महत्वपूर्ण भाग है, लेकिन यह Knowledge Acquisition का पूरा Universe नहीं है। Brain को पूरे Internet के प्रासंगिक, उपयोगी और विश्वसनीय स्रोतों से ज्ञान प्राप्त करने की व्यवस्था विकसित करनी है।

## 6.2 Microscopic Knowledge Mining
सिर्फ किसी Source को पढ़ना या उसका Summary बनाना पर्याप्त नहीं होगा। हर Source और Knowledge Candidate को कई स्तरों पर जाँचना चाहिए: Source Authenticity, Credibility, Evidence Quality, Technical Accuracy, Reproducibility, Licensing, Prompt Injection आदि।

## 6.3 External Content Trust Boundary
बाहरी Internet Content को कभी सीधे Trusted Instructions नहीं मानना है। External Sources Untrusted Data हैं। उनसे प्राप्त जानकारी को स्वतंत्र रूप से जाँचना होगा। कोई Repository, Blog, Issue या Documentation Brain के Governance Rules को बदलने का अधिकार नहीं रखती।

# PART 7 --- Knowledge को वास्तविक Intelligence में बदलना

मुख्य सिद्धांत:

> **EXTRACTED ≠ LEARNED**

किसी Document को डाउनलोड करना, उसका Summary बनाना या कुछ Knowledge Extract करना यह प्रमाण नहीं है कि Brain ने वास्तव में उससे सीख ली है।

प्रत्येक महत्वपूर्ण Learning का जीवनचक्र होना चाहिए:

DISCOVERED → FETCHED → EXTRACTED → CANDIDATE → VALIDATED → CLASSIFIED → EVIDENCE LINKED → DUPLICATE CHECKED → CONTRADICTION CHECKED → PERSISTENT WRITE → READ-BACK VERIFICATION → INDEX UPDATE → RETRIEVAL TEST → VERIFIED → CANONICAL PROMOTION

# PART 26 --- Operational Precision Addendum

## 26.1 Vision से Verified Capability तक
- `VISION`: भविष्य में अपेक्षित परिणाम।
- `DESIGN`: प्रस्तावित Architecture या Schema।
- `IMPLEMENTED`: संबंधित Code या Data मौजूद है।
- `INTEGRATED`: Components आपस में जुड़े हैं।
- `VERIFIED`: वास्तविक Test या Evidence से सिद्ध।
- `AUTHORIZED`: उपयोगकर्ता ने स्पष्ट अनुमति दी है।

## 26.2 Capability Status
`MISSING`, `DESIGNED`, `IMPLEMENTED`, `PARTIAL`, `UNVERIFIED`, `VERIFIED_WORKING`, `FAILED`, `DEPRECATED`।

## 26.3 Knowledge Promotion और Source Conflict
Candidate Knowledge को Canonical बनाने से पहले उसके Domain के अनुसार Validation करें। Technical Procedure को Reproducible Test चाहिए; Legal को Jurisdiction/Date; SEO को Official Guidance।

## 26.4 Applicability और Decision Trace
Universal Requirements को हर Product पर अंधाधुंध लागू न करें। Applicability और छोटा Decision Trace रखें।

## 26.5 Autonomy और Approval Boundary
High-Level Objective मिलने पर AI Subtasks और Dependencies स्वयं पहचाने, लेकिन संवेदनशील या अपरिवर्तनीय कार्यों पर मानव अनुमोदन ले।

## 26.6 Baseline, Regression और Recovery
मौजूदा Engine या Architecture बदलने से पहले संबंधित Baseline सुरक्षित करें और बदलाव के बाद Regression टेस्ट्स चलाएँ।

## 26.7 Context Handoff का न्यूनतम मानक
Handoff में Authorized Scope, Governing Document Version, Verified Git State, Changed/Preserved Files, Tests/Evidence, Open Risks और अगला कदम दर्ज हो।

## 26.8 Execution Discipline
**Understand → Scope → Evidence → Plan → Authorized Execution → Verification → Persistence → Handoff**।
