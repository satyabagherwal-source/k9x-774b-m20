## 2. Net-New Universal Engineering Rules (Candidates for Master Brain)

### 1. The Anchor-Heading Synchronization Invariant
**RULE**:
In any large-scale Markdown documentation system, the URL fragment (anchor) generated by a heading MUST be programmatically verified against the link target in the Table of Contents. A manual typo in an anchor (e.g., `#table-of-content` vs `#table-of-contents`) MUST be treated as a critical navigation defect, equivalent to a broken API endpoint.

**WHY**:
Forensic analysis of Commit `72826bc7` reveals that a single character typo (`s` missing in `contents`) broke the "Back to Top" navigation for multiple sections. In large documents, users rely on these anchors for context retention. A broken anchor forces the user to scroll manually, degrading UX and increasing cognitive load. In automated documentation pipelines, broken anchors indicate a desynchronization between the content structure and the navigation index.

**WHEN TO APPLY**:
Any project using Markdown for primary documentation, especially those exceeding 500 lines or containing multiple levels of nested headings.

**VERIFIED IMPLEMENTATION PATTERN**:
```markdown
<!-- Correct Heading -->
## Table of Contents

<!-- Correct Link Target (must match GitHub's slug generation: lowercase, spaces to hyphens) -->
[Back to Top](#table-of-contents)

<!-- Automated Check Script (Pseudo-code) -->
function validateAnchors(markdownContent) {
    const headings = extractHeadings(markdownContent); // e.g., "Table of Contents"
    const links = extractLinks(markdownContent);       // e.g., "#table-of-contents"
    
    const validAnchors = new Set(headings.map(h => slugify(h)));
    
    for (const link of links) {
        if (link.startsWith('#') && !validAnchors.has(link.substring(1))) {
            throw new Error(`Broken Anchor: ${link} does not match any heading.`);
        }
    }
}
```

**NEGATIVE CONSTRAINT**:
```markdown
<!-- ANTI-PATTERN: Manual typing of anchors without verification -->
## Table of Contents

<!-- BUG: 'content' instead of 'contents' -->
[Back to Top](#table-of-content)
```

**VERIFICATION METHOD**:
Run a linter (e.g., `markdown-link-check` or a custom script) that parses all `#` links and verifies their existence in the document's heading list. CI/CD MUST fail if any internal anchor is broken.

### 2. The Stale-Link Deprecation Protocol
**RULE**:
When a referenced external software project is abandoned, renamed, or replaced by an official successor, the documentation MUST NOT simply remove the link. It MUST update the reference to the current official version and explicitly note the deprecation of the previous version to prevent user confusion and security risks (abandoned software often has unpatched vulnerabilities).

**WHY**:
Issue #144 highlights that "DevToys for Mac" was abandoned. If the guide continued to link to the abandoned version, users would install outdated, potentially insecure software. The invariant is that documentation must reflect the *current* state of the ecosystem, not a historical snapshot.

**WHEN TO APPLY**:
Any documentation that references third-party tools, libraries, or services.

**VERIFIED IMPLEMENTATION PATTERN**:
```markdown
<!-- Before (Stale) -->
* [DevToys for Mac](https://github.com/abandoned-repo/devtoys-mac)

<!-- After (Corrected) -->
* [DevToys (Official)](https://github.com/davidshimjs/devtoys) 
  * *Note: The previous community fork is abandoned. Use the official version.*
```

**NEGATIVE CONSTRAINT**:
```markdown
<!-- ANTI-PATTERN: Leaving dead links without context -->
* [DevToys for Mac](https://github.com/abandoned-repo/devtoys-mac)
```

**VERIFICATION METHOD**:
Implement a "Link Rot" checker in CI that flags 404s or repositories marked as "archived" on GitHub. Additionally, maintain a manual review cycle for "Recommended Tools" sections every 6 months.
