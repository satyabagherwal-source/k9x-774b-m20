## 1. Executive Forensic Architecture & System Mechanics

### Exact Technical Problem Solved
Traditional embedded systems programming relies either on a bare-metal `super-loop` architecture (which complicates state machines, introduces jitter, and turns concurrent I/O into deeply nested callback spaghetti) or a preemptive Real-Time Operating System (RTOS) like FreeRTOS or Zephyr. An RTOS incurs non-trivial RAM overhead by allocating an isolated, statically sized stack per task (often leading to silent stack overflows or excessive memory reservation), and incurs context switch penalties (register saving/restoring across hardware context interrupts). 

`embassy` solves this by synthesizing Rust's cooperative asynchronous model (`async`/`await`) directly onto bare-metal microcontrollers without requiring an OS, dynamic heap allocation (`#![no_std]`), or multi-stack overhead. Through static dispatch and compiler-generated state machines, Embassy tasks execute on a **single shared call stack** while dormant tasks occupy only the exact compile-time known footprint of their state machines in `.bss` / `.data`.

```
+-------------------------------------------------------------------------------+
|                             Application Tasks                                 |
+-------------------------------------------------------------------------------+
|      embassy-net      |     cyw43 / Bluetooth      |    embassy-usb / Storage |
+-------------------------------------------------------------------------------+
|                         embassy-executor / Wakers                             |
|  - Lock-free RunQueue (TransferStack / MutexTransferStack)                    |
|  - Cooperative Polling / Task State Machine Bitfields (SPAWNED, RUN_QUEUED)   |
+-------------------------------------------------------------------------------+
|                     embassy-time (Driver Interface / LPTIM)                   |
|  - 64-bit Non-overflowing Monotonic Ticks / Alarm Ring Queues                 |
+-------------------------------------------------------------------------------+
|                 Hardware Abstraction Layers (HALs: STM32, NRF, RP, etc.)      |
|  - PAC (Peripheral Access Crates) / Direct MMIO Register Manipulation         |
|  - EasyDMA Zero-Copy Invariants & Flash-to-SRAM Bounce Buffer Mechanics       |
+-------------------------------------------------------------------------------+
|                 Bare-Metal Silicon (Cortex-M0+/M3/M4/M7/M33, RISC-V)          |
+-------------------------------------------------------------------------------+
```

### Architectural Subsystem Boundaries & Invariants

1. **`embassy-executor`**:
   - Implements a zero-allocation, static task scheduler.
   - Enforces synchronization using compile-time selected primitives: target-native atomics (`AtomicU32`/`AtomicU8`) on cores with atomic instructions, ARM-specific load/store layouts (`state_atomics_arm.rs`), or hardware-disable critical sections (`critical-section` crate) on architectures lacking atomic instructions (such as ARM Cortex-M0 or AVR).
   - Tasks are allocated statically inside task storage wrappers generated by procedural macros (`#[embassy_executor::task]`), guaranteeing static allocation and bounded memory utilization.

2. **The Run Queue Subsystem (`embassy-executor/src/raw/run_queue.rs`)**:
   - Implements an intrusive lock-free MPSC queue (`cordyceps::TransferStack`) using intrusive linked-list pointers located directly within the `TaskHeader`.
   - Polling tasks does not require intermediate heap buffers. Tasks are batched and reversed or sorted into priority queues (`SortedList`) depending on feature configuration (`scheduler-priority` / `scheduler-deadline`).

3. **`embassy-time` & Hardware Drivers**:
   - Abstracted from the executor. Time queues operate via globally registered symbols using a custom link-time dynamic resolution pattern (`unitrait`).
   - Translates hardware counter registers (e.g., LPTIM, RTC, SysTick) into a monotonic 64-bit timestamp (`Instant`), completely eliminating rollover bugs common in 16-bit and 32-bit timers.

4. **Hardware Abstraction Layer (HAL) & EasyDMA Boundary**:
   - Enforces hardware memory safety invariants via zero-cost type states. 
   - Protects DMA engines (such as Nordic EasyDMA or STM32 DMA/BDMA) from illegal memory access (e.g., trying to read from flash via peripheral buses that only route to internal SRAM) via automatic runtime verification and bounce buffering.

## 2. Net-New Universal Engineering Rules (Candidates for Master Brain)

### 1. Hardware-Constrained Clock Divider Floor Invariant
**RULE**:
When calculating dynamic clock prescalers, PLL divisions, or counter periods against a ceiling target frequency ($F \le F_{\text{target}}$) or minimum interval bound, code MUST use floor-logarithm integer math (`checked_ilog2()`) rather than ceiling power-of-two calculations (`next_power_of_two()`). If an exact divisor cannot be realized, the calculation MUST either reject the configuration or round toward a strictly safer/lower clock frequency.

**WHY**:
Using `next_power_of_two().trailing_zeros()` rounds partial fractional quotients *upward* to the next power of two. When dividing a master base clock ($F_{\text{base}}$) by an upward-rounded prescaler ($2^{\text{trial\_ps}}$), the calculated divisor becomes larger than requested, causing the resulting operational frequency to drop below acceptable bounds, failing assertions, or worse, rounding downward in inverted equations and driving hardware beyond its physical electrical clock specifications (overclocking/overdividing registers).

**WHEN TO APPLY**:
Hardware Abstraction Layer (HAL) clock tree configuration, display refresh rate generation (LCD/OLED), UART baud rate generators, I2C/SPI bus divider calculations, and timer prescaler logic on bare-metal systems.

**VERIFIED IMPLEMENTATION PATTERN**:
```rust
/// Calculates the optimal clock divider prescaler without over-dividing.
///
/// Ensures the calculated frequency never violates hardware target bounds.
pub fn calculate_prescaler(
    clock_freq_hz: u32,
    target_hz: u32,
    duty_divider: u32,
) -> Option<(u8, u32)> {
    let target_division = clock_freq_hz.checked_div(target_hz * duty_divider)?;
    let mut best_match: Option<(u8, u32)> = None;

    for trial_div in 0..0x0F {
        let divisor_base = trial_div + 16;
        let quotient = target_division / divisor_base;
        
        // SAFE: checked_ilog2 computes floor(log2(x)), ensuring prescaler does not over-divide
        let Some(trial_ps) = quotient.checked_ilog2() else {
            continue;
        };

        if trial_ps > 7 {
            continue; // Hardware prescaler bitfield width restriction
        }

        let actual_hz = clock_freq_hz / ((1 << trial_ps) * divisor_base) / duty_divider;
        
        // Invariant: Select the closest frequency that does NOT exceed target
        if actual_hz <= target_hz {
            match best_match {
                None => best_match = Some((trial_ps as u8, actual_hz)),
                Some((_, prev_hz)) if actual_hz > prev_hz => {
                    best_match = Some((trial_ps as u8, actual_hz));
                }
                _ => {}
            }
        }
    }

    best_match
}
```

**NEGATIVE CONSTRAINT**:
```rust
// ANTI-PATTERN: NEVER use next_power_of_two() when calculating divider exponents!
// If target_division / divisor_base is 5, next_power_of_two() yields 8 (power 3).
// (1 << 3) = 8 instead of 4, causing massive clock underflow and assertion crashes!
let trial_ps = (target_division / (trial_div + 16))
    .next_power_of_two()
    .trailing_zeros(); // CRASH: Produces oversized divider!
```

**VERIFICATION METHOD**:
Property-based testing using `proptest` verifying that for any randomized `clock_freq_hz` $\in [1\text{MHz}, 500\text{MHz}]$ and `target_hz` $\in [10\text{Hz}, 1\text{MHz}]$, the generated frequency satisfies $F_{\text{actual}} \le F_{\text{target}}$ and does not panic on any quotient boundary.

### 2. Dual Logging Format Compatibility Rule
**RULE**:
In embedded library code supporting both standard `log` and binary logging frameworks (`defmt`), format arguments referencing enumerated types, Peripheral Access Crate (PAC) values, or hardware status descriptors MUST use Debug formatting (`{:?}`) instead of Display formatting (`{}`).

**WHY**:
The `defmt` logging framework provides internal macro transformations that synthesize pseudo-display formats for raw bitfields and enums via custom trait derivations. Conversely, standard `core::fmt::Display` is deliberately not implemented for generated PAC register values or internal driver enums to save code footprint. Using `{}` compiles cleanly when `defmt` is active, but triggers catastrophic build failures under standard `log` configurations (`the trait core::fmt::Display is not implemented for ...`).

**WHEN TO APPLY**:
All Rust embedded drivers, operating system kernels, HAL crates, and `no_std` libraries that support multi-backend logging flags (e.g., `feature = "log"` alongside `feature = "defmt"`).

**VERIFIED IMPLEMENTATION PATTERN**:
```rust
// Macro abstraction harmonizing logging backends safely
#[cfg(feature = "defmt")]
use defmt::{debug, trace};
#[cfg(all(feature = "log", not(feature = "defmt")))]
use log::{debug, trace};

#[derive(Debug, Copy, Clone, PartialEq, Eq)]
pub enum LowPowerMode {
    Stop0,
    Stop1,
    Stop2,
}

pub fn log_power_transition(mode: LowPowerMode, raw_bits: u32) {
    // SAFE: Uses {:?} which is universally derived across all PAC and domain types
    debug!("power: transition requested to mode: {:?}", mode);
    trace!("power: raw status register bitfield: {:#010x}", raw_bits);
}
```

**NEGATIVE CONSTRAINT**:
```rust
// ANTI-PATTERN: Breaks immediately when compiled with --features=log
// Works ONLY under defmt, introducing broken CI matrix dependencies

```

### 3. Direct Memory Access (DMA) Memory Bus Containment Invariant
**RULE**:
Before initiating a DMA bus transfer, peripheral drivers MUST verify at runtime that source and destination memory buffers physically reside within the DMA engine's accessible memory bus address range. If buffers reside in non-DMA accessible regions (e.g., Flash, tightly-coupled memories (CCM/DTCM), or external cache boundaries), the driver MUST route the transfer through an SRAM bounce buffer.

**WHY**:
Microcontroller peripheral DMA engines (such as Nordic EasyDMA or certain STM32 AHB masters) do not have bus-matrix interconnect access to Flash memory address space (e.g., `0x0000_0000..0x2000_0000`). If a driver passes a string literal or constant lookup table stored in Flash directly to a DMA address register, the DMA engine silently reads erroneous data (often `0x00` or memory fault traps), corrupting the external bus without raising a CPU-level panicking exception.

**WHEN TO APPLY**:
All low-level bare-metal DMA drivers (SPI, UART, I2C, CRYPTO, Display) operating on microcontrollers with segmented bus matrices (e.g., nRF52/nRF53, STM32F4/F7/H7, RP2040/RP2350).

**VERIFIED IMPLEMENTATION PATTERN**:
```rust
const SRAM_LOWER: usize = 0x2000_0000;
const SRAM_UPPER: usize = 0x3000_0000;
const BOUNCE_BUFFER_SIZE: usize = 256;

/// Verifies whether the specified buffer slice is entirely contained inside SRAM.
#[inline(always)]
pub fn is_slice_in_ram<T>(slice: &[T]) -> bool {
    if slice.is_empty() {
        return true;
    }
    let start_addr = slice.as_ptr() as usize;
    let byte_len = core::mem::size_of_val(slice);
    
    // Check for pointer overflow and physical boundary constraints
    match start_addr.checked_add(byte_len) {
        Some(end_addr) => start_addr >= SRAM_LOWER && end_addr <= SRAM_UPPER,
        None => false,
    }
}

/// Executes DMA transfer, falling back to stack bounce buffering if data is in Flash.
pub fn execute_dma_safe<F>(data: &[u8], max_chunk_size: usize, mut dma_transfer: F)
where
    F: FnMut(&[u8]),
{
    if is_slice_in_ram(data) {
        // Direct zero-copy transfer over AHB bus
        for chunk in data.chunks(max_chunk_size) {
            dma_transfer(chunk);
        }
    } else {
        // Fallback: Copy via stack bounce buffer to avoid bus faults
        let mut bounce_buf = [0u8; BOUNCE_BUFFER_SIZE];
        let chunk_limit = max_chunk_size.min(BOUNCE_BUFFER_SIZE);
        
        for chunk in data.chunks(chunk_limit) {
            bounce_buf[..chunk.len()].copy_from_slice(chunk);
            dma_transfer(&bounce_buf[..chunk.len()]);
        }
    }
}
```

**NEGATIVE CONSTRAINT**:
```rust
// ANTI-PATTERN: Directly passing arbitrary slices to hardware DMA registers!
// If data points to a compile-time static in .rodata (Flash), hardware reads garbage!
unsafe {
    pac::SPIM0.txd.ptr.write_value(data.as_ptr() as u32);
    pac::SPIM0.txd.maxcnt.write_value(data.len() as u32);
    pac::SPIM0.tasks_start.write_value(1); // SILENT CORRUPTION
}
```

**VERIFICATION METHOD**:
Static analysis assertion and unit tests asserting address boundaries:
```rust

    assert!(is_slice_in_ram(&stack_val));
    
    // Static constant located in Flash (.rodata)
    static FLASH_VAL: [u8; 4] = [0xAA, 0xBB, 0xCC, 0xDD];
    assert!(!is_slice_in_ram(&FLASH_VAL));
}
```

## 3. Forensic Real Incidents & Production Patches

### Incident 1: LCD Clock Divider Overflow Assertion Crash (BUG-STM32-LCD-01)
- **Context**: `embassy-stm32/src/lcd.rs`
- **What Was Expected**: When configuring an LCD peripheral with a requested target frames-per-second (`config.target_fps`), the clock divider loop should calculate the closest valid hardware prescaler (`ps`) and division factor (`trial_div`) that produces a refresh rate matching or safely below the target frequency.
- **What Actually Happened**: The calculation utilized `next_power_of_two().trailing_zeros()`. If the quotient `(target_division / (trial_div + 16))` was not an exact power of two, `next_power_of_two()` rounded upward to the subsequent power of two. This resulted in an oversized clock divisor, causing `fps < config.target_fps.0` to continuously evaluate to `false` across all iterations. The loop exited without matching a frequency, triggering a hardware assertion panic during initialization.
- **Evidence in Repo**: Commit `c88895b6`.
- **Root Cause**: Rounding up a clock divisor decreases the frequency excessively, whereas the hardware requirement was to compute the floor power of two (i.e. not exceeding the required division factor).
- **Remediation Code Diff**:
```rust
<<<< [c88895b6] embassy-stm32/src/lcd.rs
-            let trial_ps = (target_division / (trial_div + 16))
-                .next_power_of_two()
-                .trailing_zeros();
+            let Some(trial_ps) = (target_division / (trial_div + 16)).checked_ilog2() else {
+                continue;
+            };
             let fps = lcd_clk.0 / ((1 << trial_ps) * (trial_div + 16)) / duty_divider;
====
```
- **Lesson**: Mathematical rounding directions must match physical hardware implications: Divisors must be floor-rounded (`checked_ilog2()`) when lower-bound frequencies must be preserved.

### Incident 4: Monolithic Flash Update Memory Aliasing & Granularity Mismatch (BUG-BOOT-DFU-04)
- **Context**: Bootloader firmware updater, Issue #7373
- **What Was Expected**: Firmware update handlers should support block-erase and page-write sizes matching the underlying flash memory hardware characteristics (e.g., 64KB sector erases, 256-byte page writes on modern flash).
- **What Actually Happened**: The built-in `write_firmware` primitive was hardcoded to 4KB sector erases with 4-byte writes, introducing an order-of-magnitude write amplification penalty. Additionally, `prepare_update` returned a mutable reference that held an exclusive borrow across subsequent asynchronous network receives, triggering compiler borrow-checker errors (`E0499: cannot borrow as mutable more than once at a time`).
- **Evidence in Repo**: PR #7373.
- **Root Cause**: Conflating device programming granularity with high-level command state machines and holding long-lived borrows across async yield points.
- **Remediation Code Diff**: Factored out stateless `EraseBlock` and `WriteBlock` commands, allowing caller-driven erase/program lifecycles without persisting mutable borrows across task yield points.
- **Lesson**: Async embedded APIs must never hold exclusive mutable borrows across network/IO suspension points unless strictly tied to an active, locked RAII scope.

### Incident 5: RP2350 Idle Sleep Event Starvation via Redundant Atomic Write (BUG-EXEC-RP2350-05)
- **Context**: `embassy-executor/src/raw/run_queue.rs`
- **What Was Expected**: When the executor run queue is empty, the processor core should enter a deep sleep state via `WFE` (Wait For Event) / `WFI` (Wait For Interrupt).
- **What Actually Happened**: Calling `dequeue_all()` unconditionally performed atomic write operations on the run queue head pointer. On the Raspberry Pi RP2350 (ARM Cortex-M33 / Hazard3 RISC-V), any local exclusive bus access or memory write to shared atomic structures posts an internal event flag, which prevents subsequent `WFE` instructions from suspending the core, leading to battery drain.
- **Evidence in Repo**: `embassy-executor/src/raw/run_queue.rs`, lines 89–95:
```rust
// Besides the saved write, this matters on RP2350, where any exclusive
// access posts an event that keeps the idle `WFE` from ever sleeping.
if self.definitely_empty() {
    return;
}
```
- **Root Cause**: Performing unnecessary atomic write exchanges on an already empty queue dirtied the hardware event monitor.
- **Remediation Code Diff**: Added `definitely_empty()` short-circuit check prior to popping tasks from `stack.take_all()`.
- **Lesson**: Atomic writes are not free; on modern microcontrollers with event monitors, redundant atomic modifications can prevent hardware power-saving states from taking effect.

## 4. Microscopic Code-Level Invariants

### 1. Micro-Syntax & Token-Level Precision
Embedded Rust code requires explicit verification of integer casting, bitwise masking, and pointer arithmetic:
- **Checked Logarithms vs. Shifting**: When converting linear clock divisions to power-of-two prescalers, never shift negative or out-of-bounds exponents:
  ```rust
  // DANGEROUS: If quotient is 0, quotient.ilog2() PANICS!
  // SAFE: checked_ilog2 returns None if value is 0.
  let prescaler_bits = match quotient.checked_ilog2() {
      Some(bits) if bits <= MAX_PRESCALER_BITS => bits,
      _ => return Err(ClockError::PrescalerOutOfBounds),
  };
  ```
- **Alignment Mask Arithmetic**: Alignment helper functions MUST enforce that the alignment operand is an explicit power of two using `debug_assert!`:
  ```rust
  // Embassy util.rs invariant
  pub(crate) fn round_up(x: u32, a: u32) -> u32 {
      debug_assert!(a.is_power_of_two(), "Alignment parameter 'a' MUST be a power of two");
      (x + (a - 1)) & !(a - 1)
  }
  ```
  *Hazard*: If `a` is not a power of two (e.g., `a = 3`), `!(a - 1)` does not create a bitmask, resulting in corrupted pointer calculations and misaligned memory access faults.

### 2. Infinite Loop & Resource Starvation Guards
- **Hardware Polling Loop Caps**: Drivers interacting with hardware status registers (such as crypto accelerators or PLL locks) must never execute unbounded `while` loops without watchdog or cycle bounds:
  ```rust
  // POOR: Can deadlock the entire core if silicon fails to clear status
  while !pac::CC_PKA.pka_pipe().read().status() {}

  // PRODUCTION GRADE: Bounded cycle poll with invariant check
  let mut timeout_cycles = 1_000_000;
  while !pac::CC_PKA.pka_pipe().read().status() {
      timeout_cycles -= 1;
      if timeout_cycles == 0 {
          panic!("HARDWARE DEADLOCK: CryptoCell PKA pipeline unresponsive!");
      }
      core::hint::spin_loop();
  }
  ```
- **Executor RunQueue Batch Isolation**: When iterating the task queue in `dequeue_all()`, tasks re-waking themselves during polling could trigger an infinite execution loop. Embassy avoids this by atomically detaching the queue's head via `take_all()`:
  ```rust
  // Invariant: Atomically swap out the current batch
  let taken = self.stack.take_all();
  // Any task enqueued by on_task() enters the NEW stack, NOT the active 'taken' iterator
  for taskref in taken {
      run_dequeue(&taskref);
      on_task(taskref);
  }
  ```

### 3. UI & Display Micro-Mechanics
- **Command/Data Slice Offsetting**: Low-level SPI/I8080 display drivers often prepend a 4-byte command header to transmission buffers. Indexing must maintain proper 4-byte word alignments:
  ```rust
  // cyw43/src/util.rs WriteBuffer invariant
  impl ops::Index<ops::RangeTo<usize>> for WriteBuffer {
      type Output = Self;
      fn index(&self, mut range: ops::RangeTo<usize>) -> &Self::Output {
          range.end += 4; // Reserve space for the 4-byte bus command header
          unsafe { &*(&self.buf[range] as *const Aligned<A4, [u8]> as *const [u8] as *const WriteBuffer) }
      }
  }
  ```

### 4. Backend Concurrency & Memory Safety
- **Dual-State Atomic Bit Packing (`State` in `state_atomics.rs`)**:
  Task execution states are packed into atomic integers using bitfields to prevent Time-Of-Check to Time-Of-Use (TOCTOU) race conditions:
  - Bit 0: `STATE_SPAWNED`
  - Bit 1: `STATE_RUN_QUEUED`
  
  ```rust
  // Atomic CAS ensures task cannot be spawned twice concurrently
  pub fn spawn(&self) -> bool {
      self.state
          .compare_exchange(
              0,
              STATE_SPAWNED | STATE_RUN_QUEUED,
              Ordering::AcqRel,
              Ordering::Acquire,
          )
          .is_ok()
  }
  ```
- **CriticalSection Re-entrancy Protection**: When compiling for architectures lacking atomics, `critical-section` mutexes protect task pointers:
  ```rust
  // SAFETY: Never leak the inner reference outside or invoke recursion that
  // could alias the inner cell while borrowed!
  let inner = unsafe { &mut *self.inner.borrow(token).get() };
  let is_empty = inner.is_empty();
  inner.push(item);
  is_empty
  ```

## 5. The 9 Deep Learning Dimensions

### 1. Architecture
Embassy decouples task scheduling from hardware execution via five independent layers:
- **`embassy-executor`**: Core runtime engine containing the scheduler, task arena, and `Waker` contracts. Completely unaware of concrete silicon.
- **`embassy-time`**: Clock abstraction layer defining global time drivers via stable link-time hooks.
- **`embassy-sync`**: `no_std`, heapless concurrency primitives (Channels, Mutexes, Signals, PubSub, Zerocopy RingBuffers).
- **HAL Layer (`embassy-stm32`, `embassy-nrf`, etc.)**: Safe wrappers encapsulating low-level Peripheral Access Crates (PACs).
- **Upper Protocol Stacks (`embassy-net`, `embassy-usb`, `cyw43`)**: Clean network and interface engines operating purely over generic `embedded-io-async` traits.

### 2. Core Abstractions
- **`TaskHeader`**: Intrusive node struct containing task state flags, poll function pointer, and linked list link pointers (`RunQueueItem`).
- **`TaskRef`**: Transparent raw pointer wrapper providing type-safe handles to static task storage blocks.
- **`unitrait`**: Link-time trait implementation pattern enabling global hardware singletons (like timer drivers) without dynamic dispatch or static mut pointers.
- **`Aligned<Alignment, [u8]>`**: Hardware-aligned memory wrappers ensuring DMA buffers conform to strict 4-byte, 8-byte, or 32-byte cache-line requirements.

### 3. Error Handling
- Complete exclusion of panics in drivers via `Result<T, Error>` patterns.
- Error propagation utilizes statically dispatched enums mapping direct silicon registers (e.g., `Overrun`, `Parity`, `Framing`, `BusFault`).
- Graceful degradation: If dynamic prescaler calculation fails, functions return explicit `Option::None` or domain errors rather than falling back to dangerous default frequencies.

### 4. Testing
- Native emulation harnesses: Testing executor scheduling logic on developer hosts (`x86_64`) via `std::sync` fallbacks.
- Hardware-in-the-loop (HIL) automation using custom runner scripts (`ci.sh`, `test.sh`) executing on real hardware test benches via `probe-rs`.
- Compile-time macro expansion assertions guaranteeing valid parsing of outer and inner attributes inside procedural macros (`syn::parse`).

### 5. Security & Memory Safety
- Elimination of memory corruption through `no_std` zero-allocation guarantees.
- Bounded Flash-to-RAM bounce-buffering, preventing out-of-bounds DMA read injections.
- Zeroizing sensitive registers: Cryptographic engines explicitly overwrite virtual hardware register sets and scratch registers (`clear_regs`) upon completing operations.

### 6. Performance
- **Zero dynamic allocation**: BSS size is deterministic and known at compile time.
- **Single-stack architecture**: Cooperative tasks run on the main thread stack, minimizing context-switch times to a standard function call (sub-microsecond latency).
- **Lock-free run queue**: Preemption-free MPSC task enqueueing via atomic swaps (`TransferStack`).
- **Sleep coalescing**: Idle routines drop straight to `WFE`/`WFI`, consuming microamps during dormant periods.

### 7. Deployment
- Cross-compilation across diverse target architectures: `thumbv6m-none-eabi`, `thumbv7em-none-eabihf`, `thumbv8m.main-none-eabihf`, and `riscv32imac-unknown-none-elf`.
- Complex Cargo feature matrices decoupling chip families, pin mappings, and scheduler variants (e.g., `stm32h755zi`, `nrf52840`, `rp2040`).

### 8. Agent Patterns
- Procedural code generation: `embassy-executor-macros` uses custom parsing to extract task signatures without parsing bodies as full ASTs (`ItemFn`), improving IDE code completion and caching.
- Dynamic interface resolution via `unitrait!`: Generates global symbol stubs resolved by the final application crate at link time.

### 9. Data Flow
- Inbound data path: Hardware interrupt asserts $\rightarrow$ ISR wakes task waker $\rightarrow$ Waker pushes `TaskHeader` to atomic `TransferStack` $\rightarrow$ Core exits `WFE` $\rightarrow$ Executor pops batch $\rightarrow$ Task future is polled $\rightarrow$ DMA buffer processed directly in place.
